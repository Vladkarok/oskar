## 28 — serialize clipboard-compatible emoji delivery (P1)

**Failure.** A clipboard pick starts/replaces `wl-copy` in
`Panel.qml:1210-1220`. Wine/Proton paste is emitted over several timer ticks in
`Keyboard.qml:934-974`. `Panel.qml:1257-1265` records success immediately and
cannot see `pasteCurrent()` refusing a second paste while pacing. Rapid A→B
picks can replace the clipboard before A's delayed Ctrl+V reaches the client:
A is lost, B may be pasted twice, while both are recorded as successful.

**Implementation direction.** Make clipboard publication plus paste dispatch
one owned transaction with `accepted`, `completed`, and `cancelled` outcomes.
Prefer a small state machine in `ClipboardPaste.js`; QML owns only Process and
Timer effects.

- Serialize picks. A newly accepted payload must not replace the clipboard
  owner used by an unfinished paste. Queue picks in order; do not solve this
  with another guessed delay.
- Give `Keyboard.pasteCurrent()` an explicit result/callback. For a paced
  chord, completion is after its final line is dispatched. For an immediate
  chord, completion is after all lines are accepted by the socket writer.
- Record usage, settle search, and apply close-after-pick only from completion.
- Define close/reopen behavior. Preferred: an already accepted paste finishes
  under the transaction's ownership. If cancellation is chosen, it must emit
  compensating releases for every already-sent modifier before declaring the
  transaction cancelled.
- A socket loss cancels pending callbacks and cannot count as success.

**Red tests first.** Add production-seam coverage for:

1. Proton/Wine A→B rapid picks dispatch A once, then B once, in that order.
2. A second pick cannot replace A's clipboard owner before A's paste key.
3. A busy/refused dispatch is not recorded as usage and does not close the page.
4. Close/reopen mid-chord leaves no held modifier and no stale queue.
5. Existing immediate native/terminal paths and direct `text` routes do not
   change.

**Done.** Host tests pass, the regressions are red on `dd7b0c6`, a VM Proton
leg proves two rapid real picks byte/sequence-correct, and independent review
returns `Verdict: ship`.

## 06 — recover a custom `kb_file` after shell failure (P2)

**Failure.** The user's original custom keymap path exists only in
`Keyboard.qml:500`. The panel points Hyprland at the helper-published map in
`Keyboard.qml:521-536`; restoration depends on
`Component.onDestruction` (`Keyboard.qml:566-575`). After a shell crash or
SIGKILL, a new shell sees the published path, but `userKeymapFile` is empty.
`Keyboard.qml:651-655` then feeds empty/RMLVO input back to the helper and
silently loses the supported custom map. The substring test also misclassifies
an unrelated custom path containing `/omarchy-osk/keymap.xkb`.

**Implementation direction.** Persist the original source path atomically in
the helper's runtime directory before overriding Hyprland. Runtime state is
appropriate: it must survive a shell restart in the same graphical session,
not outlive the session. Keep one authority for this value. Compare the
published path by normalized exact identity, never `indexOf()`.

A helper-owned sidecar is preferred because the helper survives a shell crash
and already owns `$XDG_RUNTIME_DIR/omarchy-osk`; expose the recovered value
through the existing protocol or a narrowly versioned addition. If the
protocol changes, bump both ends and test the mismatch UI. A QML-owned atomic
runtime sidecar is acceptable only if it has one writer and its crash ordering
is proven.

**Red tests first.** Cover clean destruction, shell SIGKILL with helper alive,
helper restart in the same session, an edited custom file at the same path, and
an unrelated path whose suffix resembles the published path.

**Done.** After an abnormal shell restart, caps and typing still derive from
the user's custom file; a normal session exit restores the compositor's source;
no published OSK map is ever adopted as user input.

## 31 — bound remembered layout group to the current keymap (P2, new)

**Failure.** `LayoutDevices.select()` accepts any non-negative remembered
integer (`LayoutDevices.js:133-146`). `Keyboard.qml:619-683` forwards it after
the configured list may have shrunk. The daemon accepts unbounded `configure`
and `group` values (`daemon/src/main.rs:2814-2818`), while `caps` later rejects
the same group. With weak live device evidence, a stale group 2/3 against a
one/two-group map can leave current caps unavailable and typing gated.

**Implementation direction.** At the selection seam, derive the selected
reading's non-empty layout count and accept a remembered group only in
`0..<count`; otherwise use the existing valid consensus/current fallback. Add
defence in depth in Rust: validate both configure group and `group <n>` against
the compiled/installed group's count before changing device state. Preserve
the XKB-wide persisted domain 0–3 in `Config.js`; the defect is validity
against the current map, not JSON syntax.

**Red tests first.** Cover four→two and two→one layout shrink with diverged safe
devices and no current/named evidence, plus daemon rejection of out-of-range
configure/group without changing the previously installed group.

**Done.** No panel path requests caps or typing for a group outside the current
keymap; invalid socket commands fail closed without mutating device state.

## 32 — coherent AUR lifecycle and dependency contract (P1, new)

The current `PKGBUILD` is a prototype, not publishable. Its default Git source
still resolves to old `master`; `.SRCINFO` is absent. It lists only `gcc-libs`
and `glibc` as hard dependencies even though the helper links
`libxkbcommon.so.0`, the UI requires Omarchy/Quickshell/Hyprland, and required
features execute `wl-paste`/`wl-copy`. The dependency probe omits
`wl-clipboard`. Sound documents both QtMultimedia and ffmpeg but only the first
is an optdepend.

The packaged payload excludes `install.sh` (`Makefile:19-26`), but protocol
recovery always copies its source-checkout path (`Panel.qml:408-416`). Package
notes create a registration symlink and enable the service, but do not reliably
rescan and enable the plugin. Upgrade does not explicitly restart the helper or
reload the kept QML instance.

**Implementation direction.** Install one user-facing executable,
`/usr/bin/omarchy-osk`, from the package; make the source installer install the
same command under the user's path. Keep package installation non-activating:
package hooks run as root and must not guess a user's session bus.

Required commands:

- `omarchy-osk setup`: preflight dependencies; detect source-install unit
  overrides; register exactly `/usr/share/omarchy-osk/plugin` under the stable
  plugin id; rescan; enable the plugin through official Omarchy commands;
  daemon-reload; enable/start the user service. Idempotent on a correct setup.
- `omarchy-osk upgrade`: verify registration, daemon-reload, restart the helper
  in a live graphical session, and perform the shell restart needed for the
  packaged keep-loaded QML. Report each completed phase so rerun is safe.
- `omarchy-osk status`: report package payload, registration target, plugin
  enabled state, unit enabled/active state, socket presence, and protocol
  compatibility without changing state.
- `omarchy-osk teardown`: disable the plugin through Omarchy, disable/stop the
  unit, and unlink only a registration symlink whose resolved target is the
  packaged payload. Preserve config/state. Refuse foreign directories and Git
  checkouts rather than overwriting/removing them.

Legacy source artifacts in `~/.config/systemd/user` override the packaged unit.
Detect and report this. Migration must be explicit and recoverable; never
silently delete an unknown user file.

Package requirements:

- Declare every direct runtime dependency. At minimum reconcile `omarchy`,
  `hyprland`, `quickshell`, `jq`, `systemd`/udevadm, `libxkbcommon`, and
  `wl-clipboard` with the actual package boundary. `libxkbcommon` and
  `wl-clipboard` are hard requirements for the current product.
- Add both `qt6-multimedia` and `ffmpeg` as sound optdepends, or remove the
  feature's dependency on either.
- Make the panel's recovery action call the installed lifecycle command. It
  must also work from a source installation.
- Prefer a stable tagged `omarchy-osk` package as the public default. Its source
  is the public release tag with a real checksum. `omarchy-osk-git` may be a
  separate optional VCS package.
- Generate `.SRCINFO` from the final recipe. Build in a clean Arch chroot and
  inspect the produced package with `namcap` and `ldd`.
- A package install/upgrade message may tell the user to run the lifecycle
  command; it does not execute user-session mutations as root.

**Acceptance choreography in the VM.** Clean install → status → setup twice →
protocol check → upgrade → helper and shell reload check → teardown twice → no
dangling unit/plugin link → reinstall → legacy source-install migration → cold
boot. The whole run uses no developer checkout.

**Done.** One documented command turns the installed package into a working
panel and helper; upgrade cannot leave incompatible loaded halves; teardown is
safe and idempotent; clean-chroot build and VM choreography pass; independent
review returns `Verdict: ship`.

## Post-release backlog — not blockers for the Omarchy v1

1. **Three/four-layout chooser.** Highest product priority because shared
   layout state is the differentiator.
2. **Long-press accents.** Keep it layout/keymap-derived; avoid a second static
   character authority.
3. **Localization.** Externalize UI strings and generate locale-specific CLDR
   search data; current UI/search is English-only.
4. **Accessibility and touch.** Main cap `MouseArea`s lack accessible
   role/name/state (`Keyboard.qml:2038`), as does the language control. Expose
   labels, disabled state and modifier latch/lock; validate assistive technology,
   real touch cancellation/repeat, and enlarge 24–30 px chrome targets.
5. **Full-QML load gate.** Pure reducers are strong, but host tests do not load
   `Panel.qml`/`Keyboard.qml`, and `qml-check.sh` can skip when types are absent.
   Preserve a VM gate that loads the real shell surfaces and checks logs.
6. **Delivery policy.** Chromium and Wine routing are class-name heuristics
   (`EmojiPage.js:212-215`, `ModifierReducer.js:213-221`). Move policy behind one
   interface when a measured consumer requires change; do not generalize from
   names alone.
7. **Protocol hardening.** The private same-user socket has four client slots
   and unbounded `read_line()` input (`daemon/src/main.rs:2377-2454`). A line
   cap and idle pre-handshake timeout would improve availability, but this is
   not a cross-user security boundary or a v1 blocker.
8. **Catalogue loading.** Measure shell startup/memory before lazily loading the
   generated 3,883-line emoji catalogue. Optimize only with evidence.

## Architecture direction after release

Keep Qt/QML. GTK would discard the mature frontend without solving compositor
authority, focus, XWayland, or secure Wayland input.

The helper's versioned socket is already a deep module: a small interface hides
XKB compilation, keycap facts, held-key claims, text delivery, and Wayland
ordering. The pure JS reducers also have good locality. The weak seam is the UI:
`Keyboard.qml` mixes rendering, Hyprland discovery/keymap policy, socket
lifecycle, and dispatch; `Panel.qml` mixes surfaces, persistence, clipboard,
sound, lifecycle, and output policy.

After v1, extract behavior while preserving the current external result:

1. internal helper modules for protocol, XKB/keycap planning, input
   transactions/claims, and the Wayland adapter;
2. narrow QML interfaces for `InputTransport`, `CompositorSession`,
   `ClipboardDelivery`, `Persistence`, and `Theme`;
3. current Hyprland/Omarchy implementations become the first adapters;
4. add a standalone Qt/QML or generic Quickshell host as the second real
   adapter, initially for another wlroots compositor;
5. pursue Mutter/KWin cooperation as desktop-specific adapters. A universal
   Linux OSK is not one toolkit rewrite: Wayland deliberately makes global
   input and layout ownership compositor policy.

Do not split files mechanically. Extract one module when a behavioral ticket
touches that responsibility, put tests at its interface, and preserve the
existing VM evidence.
