В этих сессиях commit/push не выполнялись. Публикация репозитория, AUR и push
остаются отдельными действиями по указанию владельца. Запуск новой сессии
текстом из конца документа поручает работу по этапам A–E, включая локальные
commits; push и публикацию он не разрешает.

Commit — не резервная копия. `git checkout .` откатит правки tracked файлов,
но не тронет untracked; сбой диска не переживёт ни рабочее дерево, ни локальный
commit. От потери диска защищают только push в приватный origin или внешняя
копия. Это решение владельца: спросить его в начале сессии.

Локальная доска `.scratch/next-iteration/` игнорируется Git. Она не переживёт
новый clone. Поэтому критические сведения сохранены здесь, а не только в тикетах.
Игнорирование доски выбрано сознательно; достаточно держать durable specs и
handoff в Git и настроить backup — решение владельца (F9).

## 2. Продукт и границы первого релиза

Это мышиная экранная клавиатура для **Omarchy + Hyprland + Quickshell**.
Главная ценность — keycaps соответствуют фактическому вводу и следуют системной
раскладке в обе стороны. Rust helper держит долгоживущую virtual keyboard;
QML отвечает за отображение, настройки и взаимодействие.

Сильные стороны: проверяемые state machines, корреляция ответов/configure,
защита от залипших клавиш, восстановление соединения, unit и реальные VM
integration tests. Основной риск — взаимосвязанные состояния на стыке compositor,
QML и приложения; зелёные чистые JS-тесты не доказывают поведение этих стыков.

KDE/GNOME/Xorg сейчас не поддерживаются. UI зависит от Omarchy imports и
Hyprland IPC; helper требует `zwp_virtual_keyboard_manager_v1`. Даже поддержка
этого протокола другим compositor не переносит синхронизацию раскладок и UI.
XWayland-приложение внутри Hyprland не равно отдельной Xorg-сессии.
Переносимость — последующее направление, не условие первого релиза.

## 4. Проверки и установленное состояние

Последний полный host-прогон:

```sh
./tools/run-tests.sh
cargo clippy --manifest-path daemon/Cargo.toml --all-targets -- -D warnings
git diff --check
bash /usr/share/omarchy/bin/omarchy-plugin-validate .
```

Результат: **276 test cases** в десяти QML/JS suites (это `T.test`, а не
отдельные assertions) и **38 Rust tests** проходят; Clippy и `git diff --check`
чисты. Все три прохода получили одни и те же числа; «302 checks» в handoff
устарело. Validator завершается с 1 из-за tracked symlink `CLAUDE.md` (R3).
XKB errors в отрицательных fixtures ожидаемы.

Что эти проверки не доказывают:

- Тесты проверяют логику отдельных JS-функций, но почти не проверяют, как
  настоящий QML связывает их между собой. R1 и R2 — именно такие ошибки.
- `tools/qml-check.sh` ловит один класс сообщений qmllint (обработчик
  несуществующего сигнала), проходит при отсутствии инструмента или types и
  смотрит только tracked QML: untracked `HoverTooltip.qml` не проверен (R4).
  Зелёный результат не означает, что UI загружается.
- Графическая приёмка Panel/Process/Timer не запускалась; изменения 25/27 в VM
  не проверялись. Историческая запись тикета 26: 30 VM tests, 68 keymap
  rebuilds; старые цифры «44–52» и «36 helper tests» в handoff устарели. Не
  менять churn ceiling наугад.

Host plugin — symlink в рабочее дерево; `omarchy restart shell` выполнен после
QML-изменений. В этой сессии helper **не переустанавливался** после двух
Clippy-правок Rust. Они не меняют алгоритм, но предыдущая фраза «Rust не менялся»
была неточной. При дальнейших Rust изменениях соблюдать `./install.sh` workflow.

Не запускать экспериментальный helper или nested compositor в рабочей host
сессии. Для integration использовать VM; сначала прочитать `docs/vm-handoff.md`
и проверить `ssh -o ConnectTimeout=5 omarchy-vm true`. Состояние VM заново
проверить, не считать старое «running» текущим фактом.

Каждое из них уже стоило проекту времени:

## 5. Находки: сводка трёх проходов

Основа сильная: reducer модификаторов, generations у configure, claims и
отдельный helper с понятными обязанностями хорошо проверены. Но в связке UI и
логики найдены две ошибки поведения, а часть сценариев доставки не измерена.
Приоритет — поведение и его проверка, а не разбиение файлов. Буква R —
[повторное ревью](review-astra-2026-09-11.md), F —
[первое ревью](review-2026-09-11.md); строки и доказательства там.

### Ошибки поведения — этап B

- **R1 — Recent показывает один оттенок, вставляет другой (P2).** Плитки Recent
  идут через общий delegate сетки, который всегда просит заново применить
  текущий оттенок; Most Frequent этого не делает. Сохранённый `👍` после выбора
  тёмного оттенка рисуется как `👍`, а вставляется `👍🏿`. Уже тонированные
  записи не меняются, поэтому проверки на них скрывали дефект. Воспроизведено на
  production JS в Node, не в живом UI. Исправление: retone определяется
  происхождением плитки; история повторяет точные данные.
- **R2 — paste при открытом emoji search уходит во внешнее приложение (P1).**
  `pasteCurrentContent()` знает только локальный ввод цветового поля; после
  probe chord уходит сфокусированному клиенту. Действие попадает не в ту цель.
  Воспроизведено вызовом функций Panel с подменённым вводом. Исправление: одно
  определение цели (emoji search, цветовое поле, внешний клиент) до выбора
  способа доставки; локальное чтение clipboard ограничить по времени и защитить
  от смены или закрытия цели.

Для обеих regression должен падать на старом коде и проходить через seam, где
QML выбирает поведение. Практически: вынести решение («retone или нет», «куда
paste») в чистую JS-функцию, которую вызывает QML, и тестировать её на реальных
входах. Затем независимое review.

### Проверки, которых не хватает — этап C

- **R4 — нет загрузки настоящего UI.** Gate: shell в VM загружает Panel и
  Keyboard из текущего дерева, в логе нет QML-ошибок, открываются панель, emoji
  page и settings. Не превращать все известные ложные предупреждения qmllint в
  ошибки одним переключателем.
- **F4 — длинная доставка под мьютексом.** Мьютекс нужен для атомарности
  swap/restore, поэтому просто отпустить его на время sleep нельзя. Но
  Chromium-маршрут спит `(6 + число hex digits) × 10 мс` на скаляр: семья
  `👨‍👩‍👧‍👦` ≈ 740 мс, 16 пятизначных скаляров ≈ 1.76 с только запланированных
  пауз. Всё это время за доставкой стоят и следующие команды самой панели.
  Shutdown ждёт тот же мьютекс не дольше 500 мс, затем процесс выходит. Тикет 17
  записал, что Hyprland не отпускает клавиши уничтоженного устройства, поэтому
  риск залипания реален; повторное ревью считает его недоказанным для этого
  сценария. Нужен воспроизводимый тест до релиза: SIGTERM посреди ZWJ-доставки,
  физический ввод и смена фокуса во время composition. Transient US-keymap живёт
  почти секунду, а не 60 мс из §39. Исправление выбирать по результату.
- **Разная изоляция модификаторов в двух маршрутах.** `text` оставляет
  удерживаемые Ctrl/Alt/Super, `text-unicode` снимает всё удерживаемое. При двух
  клиентах `down LCTL` одного и `text` другого могут подавить текст или вызвать
  shortcut. Проверить на названном потребителе. Это довод за общий transaction
  interface с явной политикой модификаторов.
- **F11 — роутинг Chromium пропускает приложения.** Подстроки класса окна не
  совпадают у VS Code (`code`), VSCodium, Obsidian, Vivaldi, Opera, Element; по
  §40 они, вероятно, получат искажённые emoji. Это вывод, а не измерение: проба
  Electron совпадает только из-за `electron` в имени. Проверить пробой под другим
  app_id; решать в §6.

### Установка и lifecycle — этап D2

- **R3 — validator отклоняет plugin.** `omarchy-plugin-validate` завершается с 1
  из-за tracked symlink `CLAUDE.md`. Варианты, решает владелец: обычный файл
  `CLAUDE.md` с одной строкой `@AGENTS.md` (Claude Code поддерживает импорт) или
  runtime payload без developer-файлов. `.agents/` игнорируется Git и в clone не
  попадает, но не должен попасть и в собранный вручную payload.
- **R5 — exit codes helper и unit не согласованы.** Unit не перезапускает helper
  при коде 78, но helper этот код не использует: постоянные ошибки старта (нет
  протокола, нет seat, второй экземпляр) выходят с 1 и повторяются до
  StartLimit. Разделить временные и постоянные отказы, согласовать коды с unit,
  проверить в VM.

### Мелкие исправления — этап B, после R1/R2

- **F5 — мёртвые ветки ответов** в `Keyboard.qml` после protocol 5. Там же
  исправить ложные контракты в комментариях: описание `sendText` всё ещё
  говорит о старых ответах.
- **Обратная связь при отказе.** Отказ доставки emoji сейчас не виден
  пользователю: `text-err` уходит в console и в `inputStatus`, который никто не
  читает. Решить, что пользователь видит, например hint как у paste chip; затем
  подключить `inputStatus` или удалить его.

## 6. Emoji, clipboard и Proton: следующий функциональный вопрос

Сейчас выбор emoji **не пишет clipboard**. Обычный путь — helper `text`
(transient keymap); Chromium/Codex — `text-unicode` (Ctrl+Shift+U, hex, Enter).
Короткий `U+...` — видимый preedit этого способа. Paste-chip читает ранее
скопированное содержимое и не является механизмом доставки выбранного emoji.

Новый отчёт владельца: Proton показывает `?` и другие символы, а Emote через
copy/paste вставляет правильно. Старые измерения Wine (§33/§39) согласуются
с этим: преобразование в Windows VK теряет требуемое значение. Однако точное
новое приложение/игра, Proton version и поле **не названы**, новый симптом
здесь не воспроизведён. Не выдавать старую причину за новый измеренный диагноз.

Рекомендация для следующего тикета (номер **28 только предложен**; первое
ревью тоже занимало 28 под разбиение `main.rs`, поэтому брать следующий
свободный номер): явный режим clipboard compatibility для emoji. Direct
сохраняет текущую гарантию; compatibility публикует emoji как Unicode clipboard
payload и отправляет paste в целевое приложение. Пользователь предложил такой
путь; конкретные default, UI и запоминание по приложениям пока не утверждены.

Порядок: сначала R1/R2 (этап B) и измерения длинной доставки (этап C), затем
проектирование compatibility с владельцем. Определение цели из R2 и выбор
маршрута здесь — одна задача; проектировать их вместе.

Условия реализации:

1. Уточнить реальное Proton-приложение/поле, создать повторяемый пример с
   direct и clipboard для одного payload. Проверить, поддерживает ли поле Paste.
2. Согласовать узкое изменение нынешней спецификации «never clipboard» именно
   для emoji compatibility. Обычные клавиши и символы не переводить на clipboard.
3. Явно показать, что compatibility **заменяет clipboard**. Сохранение/возврат
   одной текстовой строки не сохраняет картинки, HTML и все MIME-типы.
4. Владелец selection должен переживать закрытие popup; публикация должна
   завершиться до chord. Не воспроизвести умерший owner из тикета 25.
5. Учесть фокус, порядок повторных кликов, отмену, таймаут и смену selection.
   Не логировать чужое содержимое clipboard и не хранить его в state.
6. Не retry автоматически после `text-ok`: helper подтверждает отправку,
   а не правильный текст в клиенте. Иначе возможны дубли и двойные действия.
7. Usage не считать подтверждённой вставкой приложения: clipboard route может
   подтвердить publication/chord, но не фактическое принятие текста.
8. Проверить в реальном Proton, Wayland, XWayland и Chromium; emoji с skin tone,
   флагом и ZWJ; закрытие popup, повторные picks, clipboard lifetime.

Per-app policy полезна, но может быть второй итерацией. Широкие совпадения
`edge`/`chrom` по произвольной подстроке сейчас хрупки; при работе над routing
выделить проверяемый модуль выбора способа и контролируемые client identities.
Главный риск там — не ложные срабатывания, а пропуски (F11): распространённые
Electron-приложения вроде VS Code не совпадают ни с одной подстрокой. Один из
вариантов для оценки — узнавать runtime Chromium по файлам рядом с исполняемым
(`resources.pak`, `chrome_100_percent.pak` есть и у Chromium, и у Electron), а
не по имени. Это идея, не решение.

## 7. Распространение: AUR и Omarchy

**Уточнение прежнего совета:** helper не запрещает быть Omarchy plugin.
Он означает дополнительную устанавливаемую зависимость. Официальный Basecamp
plugin тоже требует отдельно установленный CLI. Принятие в registry зависит
от правил registry; его нельзя заранее объявить невозможным.

Ограничение plugin installer реальное: add/update/remove не собирают Rust,
не выполняют install/uninstall hooks и не управляют нашим systemd unit.
Это подтверждено `docs/plugin-lifecycle-analysis.md`. Там же найден release
blocker, и повторное ревью его воспроизвело: validator отклоняет дерево из-за
tracked symlink `CLAUDE.md` (R3, §5). Developer symlinks вроде
`.agents/skills/board` тоже нельзя публиковать как runtime payload.
Проверить актуальный validator перед выбором layout пакета.

AUR — разумная рекомендация для владения бинарником, unit и assets. Но
**PKGBUILD ещё не создан**, имя пакета и публикация не утверждены. AUR хранит
рецепт сборки; install/remove делает pacman. Упаковка сама по себе не решает
регистрацию plugin, запуск/остановку user unit и состояние работающего shell.

Предлагаемый пакетный layout для прототипа:

- `/usr/lib/omarchy-osk/…` — helper;
- `/usr/lib/systemd/user/omarchy-osk.service` — user unit;
- `/usr/share/omarchy-osk/plugin/` — runtime QML/JS/assets;
- `/usr/bin/omarchy-osk` — user setup/teardown/status при необходимости;
- лицензии и notices в стандартном package location.

Принцип: package() пишет только в DESTDIR/pkgdir; не в HOME сборщика и не в
живой shell. Не подменять файлы first-party `/usr/share/omarchy/shell/plugins`.
Пользовательская activation — отдельная идемпотентная операция. Способ
регистрации из `/usr/share` ещё нужно доказать: dev symlink на host не доказывает,
что такая установка разрешена validator и корректно переживёт обновление.

Нужно выбрать **одного владельца обновлений QML**. Если pacman владеет QML,
`omarchy plugin update` не должен независимо менять ту же копию. Если QML
остаётся Git plugin, описать совместимость версий с packaged helper и protocol.
Для первого релиза предпочтителен один согласованный release для QML/helper;
две независимо обновляемые части увеличивают вероятность protocol mismatch.

Проверить миграцию текущих `~/.local/libexec` и `~/.config/systemd/user` файлов:
старый user unit перекроет packaged unit и может запускать старый бинарник.
Не удалять вручную изменённые файлы без распознавания владения/backup.
Root package hooks не должны угадывать пользователя и запускать его session bus.
Удаление пакета не обязано остановить уже работающий процесс или убрать
ссылки из shell.json — это отдельные сценарии teardown. Config/state сохранять;
явный purge может быть поздней отдельной командой. Коды выхода helper
согласовать с unit до упаковки (R5).

## 9. Рефакторинг, который окупается

Владелец просил делить по логическим модулям аккуратно; не делать refactor ради
refactor. Размер main.rs (~4585 строк вместе с тестами), Keyboard (~2140), Panel
(~2000) — повод исследовать ответственность, не самостоятельный дефект.

Уже полезно выделены `ClipboardPaste.js` и `HoverTooltip.qml`. Следующие
извлечения привязывать к работе:

- Доставка/Proton: выбор маршрута и транзакция text/paste с маленьким interface.
- Helper: protocol parsing, keymap compilation/planning, text delivery,
  claims/device state; сначала один реально независимый модуль с тестами.
- Packaging: paths и lifecycle, раздельно system payload и user activation.
- Emoji settings: единый набор preset definitions и тестируемая sizing-функция.

Не создавать заранее KDE/GNOME/X11 adapters. Не проводить большие механические
переносы одновременно с исправлением поведения. Сохранить integration evidence,
после каждого связного изменения — bounded independent review по workflow.

Карта швов `main.rs` с диапазонами строк и кандидаты компонентов QML — в первом
ревью, §4: это карта для работы, не план механического переноса. Выделять по
одному модулю там, где тест фиксирует контракт; обязательной структурной
переделки до первого релиза нет. Первый кандидат — доставка: два маршрута
дублируют lift/swap/restore и по-разному обращаются с модификаторами, а R2, F4
и Proton-тикет трогают именно её. Общий transaction interface должен сохранить
атомарность, которую сейчас даёт мьютекс. При переносах сокращать
комментарии-пересказы (F3).
