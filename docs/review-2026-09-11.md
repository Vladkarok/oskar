## 2. Assessment

The core is sound and, as far as the README's survey goes, unique on
Hyprland: the system layout is the single source of truth both ways, and
delivery reaches XWayland and Electron. The helper is carefully built:
per-connection claims on held keys, a stuck-key cap enforced through the read
timeout, a signal-safe shutdown release, a connect-based second-instance
check, a hardened unit with resource limits. Decisions are recorded with their
dead ends, and tests are layered from pure JS to byte-exact consumers in a
nested compositor.

Corrected: this review called the weaknesses almost all maintainability and
process. The Astra review refuted that with two production wiring bugs, R1
and R2, which green tests and earlier ship verdicts had missed.

### F4 — the shared mutex is held across sleeps (medium, behaviour)

`apply()` (`main.rs` ~2593) takes `shared.lock()` and holds it through
`apply_locked`, which runs both delivery routes:

- `deliver_text` (~1214): one roundtrip, then `DEFAULT_TEXT_SETTLE_MS`
  (50 ms) of sleep, then the restore upload.
- `deliver_unicode_text` (~1414): per scalar, five 10 ms sleeps for the
  Ctrl+Shift+U chord, one per hex digit (4–5) and one for Enter, so about
  100–110 ms per scalar. A four-person ZWJ family (7 scalars) holds the lock
  for ≈ 0.75 s; the 16-scalar limit for ≈ 1.7 s.

Consequences, from reading the code (not measured):

1. Other connections' `tap`/`down`/`up` and `expire_stuck_keys` wait for the
   delivery. Corrected: a single panel also queues its own next commands
   behind it, so the delay is not invisible with one client.
2. Shutdown: the signal thread arms a 500 ms exit timer, then calls
   `release_everything`, which needs the same lock. A SIGTERM during a long
   Chromium delivery can exit while Ctrl (and Shift) are down. Ticket 17
   records that Hyprland does not lift a destroyed virtual keyboard's keys
   until the next physical keystroke.
3. In `deliver_unicode_text`, a failed restore upload returns `err keymap`
   without re-pressing the held keys it lifted and without restoring
   modifiers or group. The device stays on the one-group US entry keymap and
   `shared.held` disagrees with it. `deliver_text`'s equivalent failure leaves
   the transient keymap, a superset of the installed one, so it is milder.

Corrected action: the lock is also what keeps swap and restore atomic, so
releasing it during the sleeps is not a fix by itself, and recording the
limitation is not enough. Run a reproducible VM test before release (plan
§8 C): SIGTERM in the middle of a ZWJ delivery, physical typing and a focus
change during composition. Choose the fix from the measurement. Candidates:
check an atomic shutdown flag between steps and lift the chord before
leaving; raise the exit timer above the longest delivery; or sleep outside the
lock behind a delivery-in-progress guard. Make the restore-failure path
symmetric with the upload-failure path either way.

### F5 — dead code after protocol 5 (low)

`apply()` rewrites every reply to `text`/`text-unicode` into `text-ok` or
`text-err …`. `Keyboard.qml` ~1347–1353 still compares bare `err empty text`,
`err text too long`, `err no slots`, `err no level keys`,
`err no unicode keys` and `err keymap`; the `text-err` arm at ~1239 already
handles them. Remove the list and its comment; keep `err unknown command`,
which any verb can still earn.

Related: `inputStatus` (`Keyboard.qml` ~991) is assigned in 16 places and read
nowhere in any QML or JS file. Delete it or bind a visible status to it;
decide while editing.

### F6 — lenient `hello` (low)

`handle_client` (~2395) does `line.strip_prefix("hello")` and
`parse().unwrap_or(PROTOCOL_VERSION)`, so `hello`, `hello garbage` and
`helloxyz` all negotiate as the current version. Require exactly
`hello <u32>`; anything else answers `err protocol …`. Add a unit test next to
the existing parse tests.

The Astra review adds that fixed-arity verbs in `parse()` accept trailing
arguments; cover both with table-driven parser tests. Priority P3: `hello` is
a version gate, not authentication.

### F10 — looked suspicious, is fine

Recorded so the next reviewer does not re-check them:

- Socket under `$XDG_RUNTIME_DIR/omarchy-osk/` with `RuntimeDirectoryMode=0700`
  and `UMask=0077`: any process of the user can inject keys, the same trust
  boundary as any Wayland client.
- `ProtectHome=read-only` while the helper writes `keymap.xkb`: the write is
  under `$XDG_RUNTIME_DIR`, not `$HOME`.
- `install.sh` builds with `--locked`; `daemon/Cargo.lock` is tracked.
- `sendText` builds the `text-unicode` line only after `Session.textLine`
  validated the payload, so the newline check still applies.
- `pendingTextReplies` is cleared on disconnect and matched in order; the
  helper answers one line per command on one connection.
- `MAX_CLIENTS = 4` with a reconnecting panel: the rebuild drops the old
  socket first; no leak observed.

Corrected: these confirm mechanics only. They are not evidence that no other
defect exists: R1 and R2 sat next to them, and FIFO reply matching does not
say which UI target a reply belongs to.

### F11 — Chromium routing misses common apps (medium, inferred)

`needsUnicodeEntry()` (`EmojiPage.js` ~186) lowercases the focused window
class and tests it against
`/(chrom|chrome|brave|edge|electron|codex|chatgpt|openai|claude|slack|discord)/`.
`Panel.qml` ~2028 uses the result to pick `text-unicode`. The tests
(`tests/emoji-page.qml` ~231–241) cover five positives and three negatives.

Typical Wayland app_ids that match none of these (confirm with
`hyprctl clients`): VS Code `code`, VSCodium `codium`, Obsidian `obsidian`,
Vivaldi `vivaldi-stable`, Opera `opera`, Element `element`. By decisions §40,
Chromium's editor narrows a supplementary-plane keysym to one UTF-16 unit, so
these apps would likely receive a wrong character through `text`. This is
inferred, not measured. The VM Electron probe takes the Unicode route only
because its package name `osk-integration-electron` contains `electron`.

To measure: run the probe under an app_id without those substrings. One
direction to evaluate: identify the Chromium runtime by files next to the
executable (`resources.pak` and `chrome_100_percent.pak` ship with both
Chromium and Electron) rather than by name. The design belongs with the
routing module (plan §6). False positives, such as `edge` inside an
unrelated name, matter less.
